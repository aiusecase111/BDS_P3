===============================================================================
 PRACTICAL 6 — FINAL DEMO: Simple Microservice Architecture on Kubernetes
                   with Service Discovery & Load Balancing
===============================================================================

Objective:
  Deploy a simple 2-tier microservice application on Kubernetes and demonstrate
  the two most important networking concepts:

    1. SERVICE DISCOVERY  — The Frontend finds the Backend by SERVICE NAME
                            (Kubernetes DNS resolves "backend-svc" to an IP
                            automatically — no hardcoded IPs)

    2. LOAD BALANCING     — The Backend runs 3 replicas. The Service distributes
                            incoming requests across all 3 pods (round-robin).
                            Each response shows a different pod name, proving
                            that load balancing works.

  Architecture:

    User (Browser)
      |
      |  http://localhost:30100
      v
    +--------------------------------------------------+
    |  FRONTEND SERVICE (NodePort 30100)              |
    |  Type: NodePort | Exposes frontend to browser   |
    +--------------------------------------------------+
      |
      |  Kubernetes DNS resolves "backend-svc"
      |  to the Backend Service ClusterIP
      v
    +--------------------------------------------------+
    |  FRONTEND POD (Nginx)                            |
    |  Serves an HTML page that fetches from           |
    |  backend-svc via a reverse proxy                  |
    +--------------------------------------------------+
      |
      |  Proxies /api/ requests to "backend-svc:80"
      v
    +--------------------------------------------------+
    |  BACKEND SERVICE (ClusterIP)                     |
    |  Type: ClusterIP | Internal only                  |
    |  Load-balances across 3 backend pods             |
    +--------------------------------------------------+
      |              |              |
      v              v              v
    +--------+  +--------+  +--------+
    | POD 1  |  | POD 2  |  | POD 3  |
    | Nginx  |  | Nginx  |  | Nginx  |
    | "Pod1" |  | "Pod2" |  | "Pod3" |
    +--------+  +--------+  +--------+

  What you will see in the browser:
    - The frontend page loads (served by a frontend pod)
    - An auto-refreshing section fetches data from the backend
    - Each refresh shows a DIFFERENT backend pod name (load balancing!)
    - The frontend never knows the backend pod IPs — it only uses the
      service name "backend-svc" (service discovery!)

===============================================================================
 STEP 2: Create the Backend Deployment (3 Replicas)
===============================================================================

The backend is 3 Nginx pods. Each pod writes its own hostname into index.html
so we can SEE which pod responded. This is how we prove load balancing.

File: k8s-final-demo/backend-deployment.yaml
-------------------------------------------------------------------------------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: nginx:alpine
        command: ["/bin/sh", "-c"]
        args:
        - |
          echo "Backend Pod: $(hostname)" > /usr/share/nginx/html/index.html
          nginx -g 'daemon off;'
        ports:
        - containerPort: 80
-------------------------------------------------------------------------------

Explanation:
  - replicas: 3        : Three identical backend pods for load balancing.
  - image: nginx:alpine : Lightweight web server.
  - echo "Backend Pod: $(hostname)" : Each pod writes its UNIQUE pod name
    into the HTML file. When you access the backend, you see which pod
    served the request.
  - $(hostname)        : Inside a container, the hostname IS the pod name.
                         Example: "backend-7b4f6d-x9k2m"
  - containerPort: 80  : Nginx listens on port 80.

Apply it:

Command:
  kubectl apply -f k8s-final-demo/backend-deployment.yaml

Verify 3 pods are running:

Command:
  kubectl get pods -l app=backend

Expected output:
  NAME                       READY   STATUS    RESTARTS   AGE
  backend-xxxxxxxx-aaaaaa    1/1     Running   0          10s
  backend-xxxxxxxx-bbbbbb    1/1     Running   0          10s
  backend-xxxxxxxx-cccccc    1/1     Running   0          10s


===============================================================================
 STEP 3: Create the Backend Service (ClusterIP)
===============================================================================

The backend Service gives the backend pods a STABLE name and IP. The frontend
will connect to this Service by name ("backend-svc") — that is service discovery.

File: k8s-final-demo/backend-service.yaml
-------------------------------------------------------------------------------
apiVersion: v1
kind: Service
metadata:
  name: backend-svc
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
  - port: 80
    targetPort: 80
-------------------------------------------------------------------------------

Explanation:
  - name: backend-svc   : This name is registered in Kubernetes DNS.
                          Any pod in the cluster can reach it by name
                          "backend-svc" — NO IP needed.
  - type: ClusterIP    : Internal-only. The frontend (inside the cluster)
                         can reach it, but your browser cannot.
  - selector: app: backend : Routes traffic to pods with label "app: backend".
  - port: 80            : The Service listens on port 80.
  - targetPort: 80      : Forwards to the container's port 80 (Nginx).

  WHY ClusterIP for the backend?
    The backend should NOT be directly accessible from the internet.
    Only the frontend (which is inside the cluster) should call it.
    This follows the principle of least exposure — only expose what
    needs to be exposed.

Apply it:

Command:
  kubectl apply -f k8s-final-demo/backend-service.yaml

Verify:

Command:
  kubectl get svc backend-svc

Expected output:
  NAME          TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
  backend-svc   ClusterIP   10.96.x.x      <none>        80/TCP    5s

Check endpoints (the 3 backend pod IPs):

Command:
  kubectl get endpoints backend-svc

Expected output:
  NAME          ENDPOINTS                              AGE
  backend-svc   10.1.x.11:80,10.1.x.12:80,10.1.x.13:80  10s

This shows the Service is tracking all 3 backend pods. When traffic comes in,
it will be distributed across these 3 endpoints.


===============================================================================
 STEP 4: Create the Frontend (Nginx Reverse Proxy to Backend)
===============================================================================

The frontend is Nginx that serves an HTML page AND proxies /api/ requests
to the backend service. The key: the frontend connects to "backend-svc"
by NAME — it has NO IDEA what the backend pod IPs are. Kubernetes DNS
resolves "backend-svc" to the Service's ClusterIP automatically.

STEP 4a: Create the Nginx config file

The frontend Nginx needs a custom config that proxies /api/ to backend-svc.
We will embed this config directly in the deployment YAML (no separate file
needed), but for clarity, here is what the config does:

  Nginx Config (embedded in the deployment below):
  - location /         → serve index.html (the frontend page)
  - location /api/     → proxy_pass http://backend-svc:80/
                        (forward to the backend Service by DNS name)

STEP 4b: Create the frontend deployment

File: k8s-final-demo/frontend-deployment.yaml
-------------------------------------------------------------------------------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: frontend
        image: nginx:alpine
        command: ["/bin/sh", "-c"]
        args:
        - |
          cat > /usr/share/nginx/html/index.html << 'HTMLEOF'
          <!DOCTYPE html>
          <html>
          <head>
              <meta charset="UTF-8">
              <title>K8s Service Discovery & Load Balancing Demo</title>
              <style>
                  body {
                      font-family: 'Segoe UI', Arial, sans-serif;
                      background: linear-gradient(135deg, #1a1a2e, #16213e);
                      color: #eee;
                      min-height: 100vh;
                      display: flex;
                      flex-direction: column;
                      align-items: center;
                      padding: 30px;
                  }
                  h1 { color: #e94560; font-size: 2em; }
                  .subtitle { color: #888; margin-bottom: 30px; }
                  .card {
                      background: rgba(255,255,255,0.1);
                      border-radius: 15px;
                      padding: 30px;
                      width: 600px;
                      text-align: center;
                      margin-bottom: 20px;
                  }
                  .label { color: #4ecca3; font-weight: bold; }
                  .response {
                      font-family: monospace;
                      font-size: 1.2em;
                      color: #4ecca3;
                      padding: 15px;
                      background: rgba(0,0,0,0.3);
                      border-radius: 8px;
                      margin: 10px 0;
                  }
                  .history {
                      text-align: left;
                      max-height: 300px;
                      overflow-y: auto;
                      width: 600px;
                  }
                  .history-item {
                      padding: 8px 15px;
                      border-bottom: 1px solid rgba(255,255,255,0.1);
                      font-family: monospace;
                  }
                  button {
                      background: #e94560;
                      color: white;
                      border: none;
                      padding: 10px 25px;
                      border-radius: 8px;
                      font-size: 1em;
                      cursor: pointer;
                      margin: 10px;
                  }
                  button:hover { background: #c81d45; }
              </style>
          </head>
          <body>
              <h1>Kubernetes Demo</h1>
              <p class="subtitle">Service Discovery & Load Balancing</p>

              <div class="card">
                  <p><span class="label">Frontend Pod:</span> <span id="frontendPod">Loading...</span></p>
                  <p><span class="label">Backend Response:</span></p>
                  <div class="response" id="backendResponse">Fetching...</div>
                  <button onclick="fetchBackend()">Call Backend Again</button>
              </div>

              <div class="card">
                  <p><span class="label">Request History (shows load balancing):</span></p>
                  <div class="history" id="history"></div>
              </div>

              <script>
                  // Show the frontend pod name from the HTTP header
                  // Nginx adds this header (we configured it below)
                  async function fetchBackend() {
                      try {
                          // /api/ is proxied by Nginx to backend-svc
                          // This is SERVICE DISCOVERY - we just use "/api/"
                          // and Nginx + Kubernetes DNS resolve "backend-svc"
                          const res = await fetch('/api/');
                          const text = await res.text();
                          document.getElementById('backendResponse').textContent = text;

                          // Add to history to show different pods (load balancing)
                          const history = document.getElementById('history');
                          const item = document.createElement('div');
                          item.className = 'history-item';
                          item.textContent = new Date().toLocaleTimeString() + ' → ' + text;
                          history.insertBefore(item, history.firstChild);
                      } catch (e) {
                          document.getElementById('backendResponse').textContent = 'Error: ' + e;
                      }
                  }

                  // Auto-fetch every 3 seconds
                  fetchBackend();
                  setInterval(fetchBackend, 3000);
              </script>
          </body>
          </html>
          HTMLEOF

          cat > /etc/nginx/conf.d/default.conf << 'NGINXEOF'
          server {
              listen 80;

              location / {
                  root /usr/share/nginx/html;
                  index index.html;
              }

              location /api/ {
                  proxy_pass http://backend-svc:80/;
              }
          }
          NGINXEOF

          nginx -g 'daemon off;'
        ports:
        - containerPort: 80
-------------------------------------------------------------------------------

Explanation of the frontend deployment:

  THE HTML PAGE:
    - Shows "Frontend Pod: <name>" at the top
    - Has a "Call Backend Again" button
    - Auto-fetches from "/api/" every 3 seconds
    - Shows a history list of all backend responses
    - Each response shows "Backend Pod: backend-xxxxxxxx-yyyyyy"
    - As responses come in, you see DIFFERENT pod names = LOAD BALANCING

  THE NGINX CONFIG:
    - location /         → serve the HTML page
    - location /api/     → proxy_pass http://backend-svc:80/
                           This is the KEY line. "backend-svc" is the
                           Kubernetes Service name. Nginx asks Kubernetes
                           DNS to resolve it, gets the ClusterIP, and
                           forwards the request. The Service then load-
                           balances across the 3 backend pods.

  THIS IS SERVICE DISCOVERY:
    The frontend pod does NOT know:
      - The backend pod IPs (10.1.x.11, 10.1.x.12, 10.1.x.13)
      - The backend Service IP (10.96.x.x)
    The frontend pod ONLY knows the NAME "backend-svc".
    Kubernetes DNS resolves the name → Service IP → pod.
    If backend pods are recreated with new IPs, the frontend does not
    need any changes. It still uses "backend-svc" and it just works.

===============================================================================
 SUMMARY: How This Demo Proves the Two Core Concepts
===============================================================================

  CONCEPT 1: SERVICE DISCOVERY
  ---------------------------------------------------------------
  What happened:
    The frontend pod needed to call the backend. It used the name
    "backend-svc" in its Nginx config: proxy_pass http://backend-svc:80/

    The frontend pod did NOT know:
      - Any backend pod IP (they change when pods are recreated)
      - The backend Service's ClusterIP (it is assigned dynamically)

    How it worked:
      1. Frontend Nginx tries to connect to "backend-svc:80"
      2. Kubernetes CoreDNS resolves "backend-svc" → 10.96.x.x (ClusterIP)
      3. The request reaches the backend Service
      4. The Service forwards it to one of the 3 backend pods

    Why this matters:
      If backend pods are recreated, deleted, or scaled, the frontend
      config NEVER needs to change. "backend-svc" always resolves to
      the current Service IP. This is the power of service discovery —
      decouple services by name, not by address.


  CONCEPT 2: LOAD BALANCING
  ---------------------------------------------------------------
  What happened:
    The backend had 3 replicas. Each request to the backend returned
    a different pod name, proving that traffic was distributed.

    How it worked:
      1. Request arrives at the backend Service (ClusterIP)
      2. The Service has 3 endpoints (3 pod IPs)
      3. The Service picks one endpoint using round-robin
      4. The request is forwarded to that pod
      5. Next request goes to the next pod (round-robin)

    What we observed:
      - Request 1 → "Backend Pod: backend-xxxx-aaa"
      - Request 2 → "Backend Pod: backend-xxxx-bbb"
      - Request 3 → "Backend Pod: backend-xxxx-ccc"
      - Request 4 → "Backend Pod: backend-xxxx-aaa" (back to start)
      - Pattern repeats in round-robin

    When we scaled to 5:
      - Traffic was distributed across 5 pods instead of 3
      - The Service automatically included the new pods

    Why this matters:
      If one backend pod is slow or fails, traffic still goes to the
      other pods. The application stays available. Adding more pods
      increases capacity without any configuration changes.

 FACULTY VIVA Q&A
===============================================================================

Q1: What is service discovery in this demo?
A:  The frontend pod calls the backend using the DNS name "backend-svc"
    instead of an IP address. Kubernetes CoreDNS automatically resolves
    this name to the backend Service's ClusterIP. The frontend never
    needs to know the actual pod IPs, which change when pods are
    recreated. This is service discovery — finding services by name.

Q2: How is load balancing demonstrated in this demo?
A:  The backend runs 3 replicas. When the frontend sends requests to
    "backend-svc", the Service distributes them across all 3 pods using
    round-robin. Each response shows a different pod name, proving
    that different pods handled different requests.

Q3: Why is the backend Service ClusterIP but the frontend is NodePort?
A:  The backend should only be accessible from inside the cluster (by
    the frontend). ClusterIP provides internal-only access. The frontend
    needs to be accessed by the user's browser, so it uses NodePort to
    expose port 30100 externally. This follows least-privilege exposure.

Q4: What happens if a backend pod crashes?
A:  Kubernetes removes the crashed pod from the Service endpoints and
    creates a replacement. The frontend continues calling "backend-svc"
    with no changes. Traffic is routed only to healthy pods. This is
    self-healing combined with service discovery.

Q5: What happens if you scale the backend to 5 replicas?
A:  The Service automatically detects the 2 new pods and adds them as
    endpoints. Traffic is now distributed across 5 pods instead of 3.
    No frontend configuration changes are needed — the Service name
    stays the same, only the endpoints behind it change.

Q6: Why did we embed the Nginx config in the deployment YAML?
A:  For simplicity. In a real project, we would build a custom Docker
    image with the config baked in, or use a ConfigMap to inject it.
    Embedding it in the command/args keeps everything in one file for
    the demo, making it easy to follow and explain.

Q7: What is the role of the Endpoints object?
A:  The Endpoints object is automatically maintained by Kubernetes. It
    lists every pod IP that matches the Service's label selector. When
    a request arrives at the Service, it picks an endpoint (pod IP) from
    this list using round-robin. When pods are created or deleted, the
    Endpoints are updated automatically.

Q8: How does Kubernetes DNS work for services?
A:  Every Service gets a DNS record: <service-name>.<namespace>.svc.cluster.local
    For our backend: backend-svc.default.svc.cluster.local
    Pods can use the short name "backend-svc" (same namespace), or the
    full name. CoreDNS (running as a pod in kube-system namespace)
    handles the resolution and returns the Service's ClusterIP.
